# @mfbtech/changelog-generator

A changelog generator not authored by git data but by the developer implementing the fix, feature, breaking change, ...

This package helps developers manage changelogs and package version while keeping their freedom to put what ever they want in their commit messages, tags, ....

## Usage

The general workflow of a developer would be something like,

1. Branch off of the main development branch of the repository.
1. Commit changes and, before making a pull request, run `ccg change` next to the `package.json` of your project to generate a change file.
1. Create a pull requests and merge the changes. `ccg change --verify` can be run in CI/CD to verify that a change file has been generated.
1. When publishing the package, run `ccg publish` to bump the package.json version and update the changelog file with all of the change files.

Change files contain date/time, a short description of the change and an associated version bump for the change (i.e. major, minor, patch, or none).

```text
Usage: ccg [options] [command]

Options:
  -h, --help         display help for command

Commands:
  change [options]   Generates a change file if a change is detected.
  publish [options]  Combines all of the existing changes files into the change log and consolidates the version bumps in the change files down to a single version
  help [command]     display help for command
```

### change

```text
Usage: ccg change [options]

Generates a change file if a change is detected.

Options:
  -v, --verify    Verify the change file has been generated and is valid.
  -h, --help      display help for command
```

### publish

```text
Usage: ccg publish [options]

Combines all of the existing changes files into the change log and consolidates the version bumps in the change files down to a single version

Options:
  -a, --apply  By default this command will perform a readonly operation. If you want to update the change log files and the project's version (i.e. package.json), then specify this argument.
  -h, --help   display help for command
```

### Configuration

```json
{
  "repoUrl": "https://github.com/MFB-Technologies-Inc/changelog-generator.git",
  "branchName": "develop",
  "remoteName": "origin",
  "packagePath": "./package.json"
}
```

- `repoUrl`: the remote URL of the repository.
- `branchName`: the default branch name to be compared against the local branch for changes.
- `remoteName`: the default remote name for comparing against.
- `packagePath`: the path to the `package.json` of the package that should be checked for changes.

## Scripts

- `build`: Builds the CLI.
- `ccg`: Run the built CLI. Use `--` before any arguments that you want to pass to the script.
- `lint`: Fixes all lint errors.
- `check-linting`: Checks for lint errors without fixing them.
- `format`: Fixes all format errors.
- `check-formatting`: Checks for format errors without fixing them.
- `test`: Runs all tests and re-runs them when changes are made.
- `test:ci`: Runs all tests, generates a test coverage report and exits.

## Publishing

Run the version-bump workflow manually to prepare a PR. Merging that PR into the
default branch automatically tags the merge commit and publishes to GitHub and npm
in a single publish workflow.

### Repository setup

- In the npm settings for `@mfbtech/changelog-generator`, add a GitHub Actions
  **Trusted Publisher** with organization `MFB-Technologies-Inc`, repository
  `changelog-generator`, and workflow filename `publish.yml`. Leave the environment
  name empty (this workflow does not use a GitHub environment) and allow direct
  `npm publish`. This package-side configuration must be saved before releasing.
- Publishing uses GitHub OIDC with `id-token: write`, Node 24, and npm 11; no
  `NPM_TOKEN` secret is required. Release dependency caching is disabled.
  npm automatically generates provenance for this public repository. See
  [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/).
- After verifying trusted publishing works, npm recommends restricting package
  publishing to require 2FA and disallow tokens. Remove the unused `NPM_TOKEN`
  repository secret and revoke its token if it is no longer needed elsewhere.
- In Settings → Actions → General, allow GitHub Actions to create pull requests.
  The bump workflow uses `GITHUB_TOKEN`; approve any approval-required PR checks.
  See [GitHub's workflow triggering documentation](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow).
- Allow the release workflow to create version tags under the repository's rulesets.

### Prepare a version bump

1. Merge the desired changes, each with a change file generated by `ccg change`.
   At least one change must be PATCH, MINOR, or MAJOR; NONE and DEPENDENCY alone
   do not increase the version.
2. Run **Actions → version-bump → Run workflow** on the default branch.
   It builds this repository's CLI, runs `npm run ccg -- publish --apply`, updates
   the lockfile, and commits the changelogs, package files, and consumed change
   files to `release/v<version>`. It pushes that branch and opens a PR.
3. Review the PR and merge it using **Create a merge commit**, preserving history.
   Commit messages do not control release validation.
   Do not rerun the bump workflow while a bump PR is open; finish or close it and
   delete its branch first.
4. The **publish** workflow starts automatically after a same-repository
   `release/v<version>` PR merges into the default branch. It validates the version
   increase and matching package, lockfile, and changelog versions, then creates
   `v<version>` at the PR's merge commit. It never moves an existing tag.
   A rerun accepts the same tag at the same commit without recreating it; a tag
   at another commit causes a failure. If tagging fails, fix the cause and rerun
   that workflow. After tagging succeeds, the same workflow continues to publish.

For a local preview, run `npm ci`, `npm run build`, then
`npm run ccg -- publish`. Adding `--apply` writes the version and changelogs;
after applying, run `npm install --package-lock-only --ignore-scripts` to synchronize
the lockfile. `ccg publish` prepares release metadata; it does not publish to npm.

### Publish a release

1. Merging the version bump PR starts the **publish** workflow; no second manual
   action is needed. It creates the version tag once at the exact merge commit.
2. The workflow verifies the tag matches the package version, its commit is on
   the default branch, and package, lockfile, and changelog versions agree.
   It builds and tests that exact commit, then packs it with `npm pack`.
3. It creates a draft GitHub release from the version tag.
   Notes include every changelog version newer than the most recently published
   stable GitHub release, including intermediate unpublished bumps. With no
   prior release, all entries are included. NONE comments are omitted, matching
   the Markdown changelog.
4. The same `.tgz` is uploaded to GitHub and published publicly to npm. Only after
   npm succeeds does the GitHub release become public.

If tagging or publishing fails, inspect the workflow logs and fix the cause, then
rerun the failed workflow. Existing tags are reused only if they point to the same
commit; they are never moved or recreated. After a tag exists, you can also run
**Actions → publish → Run workflow** on the default branch and enter that tag
(for example, `v1.0.3`) to retry publishing. Manual retries never create tags, and
later default-branch commits do not prevent publishing the selected tag.

Retries preserve existing draft assets and compare their SHA-512 checksum with
the rebuilt package. A different artifact stops the workflow without replacement.
An already published npm version is skipped only when its registry integrity
matches the package. The workflow also verifies npm integrity after publishing
before making the GitHub release public. npm versions are immutable: if the published
package itself is wrong, create a new change and version bump. A completed GitHub
release cannot be published again by this workflow.
